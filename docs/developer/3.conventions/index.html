    3. Conventions¶

    The rules every change follows.

    Code¶

    • Use the make targets (make help): CI runs the same ones.
    • Docstrings on public functions and classes (Google style): they generate the API reference.
    • Settings through ApplicationSettings (settings.py), not os.environ scattered in the code.

    • Logging with the package's loguru logger, not print:

      from python_package_template.settings import logger

logger.info("Loaded {} items", count)

    • Log, then raise; do not swallow exceptions:

      if not os.path.exists(file_path):
    logger.error(f"File not found: {file_path}. Current directory: {os.getcwd()}")
    raise FileNotFoundError(f"The file {file_path} does not exist.")

    In an except block, logger.exception(...) logs the message and the stack trace. Not raising is fine only when the loop must go on.

    • Large data: Polars. CPU-bound work: multiprocessing.Pool.map.

    Branches and pull requests¶

    1. Branch off dev: feature/<name> or bugfix/<name>. Comment on (or create) the issue first.
    2. Keep up with dev: git merge dev if the branch is pushed, git rebase dev if it is not.
    3. Open a pull request to dev. Its title follows the commit convention below: it becomes the squash commit and decides the version.
    4. When dev is ready, a pull request dev → main releases it.
    5. After a release on main, merge main back into dev (see 5. Release).
    Merge Strategy Why
    feature/* → dev squash one conventional commit per feature
    dev → main squash one commit for semantic-release to evaluate
    main → dev (sync) merge commit, direct push squash only applies to pull requests

    Never edit project.version or create a tag by hand: semantic-release does both.

    Commit convention¶

    [emoji] <type>[(<scope>)][!]: <description>, the emoji is optional (Gitmoji).

    Emoji Type Aliases Release
    🐛 fix bugfix, hotfix patch
    ⚡️ perf patch
    ✨ feat feature minor
    💥 feat! BREAKING CHANGE: footer major
    ♻️ 📝 🎨 🧪 🔧 👷 📦 refactor, docs, style, test, chore, ci, build none

    On dev, a releasable commit bumps the release candidate instead (1.1.0-rc.1 → 1.1.0-rc.2).

    ✨ feat(auth): add GitHub App token rotation
🐛 fix(llm): handle empty response from the API
💥 feat!(api): remove the v1 endpoint

feat(auth): redesign token flow

BREAKING CHANGE: /v1/token removed, use /v2/auth instead

    Scopes are optional: github, llm, auth, agent, cache, api, ci, deps...

    Secrets¶

    • Never write a credential to a file of the repository, even untracked: use .env (git-ignored).
    • detect-secrets runs as a pre-commit hook. For a line that intentionally references a secret (${{ secrets.GITHUB_TOKEN }}), add # pragma: allowlist secret. Use the --exclude-files / --exclude-lines arguments in .pre-commit-config.yaml only for recurring, structural false positives; never exclude a whole workflow to silence one line.

    Environment variables¶

    Adding, renaming or removing one, in the same change: the setting in settings.py, .env.example, and the workflow env: if CI needs it.

    Renovate¶

    Renovate (.github/renovate.json) opens pull requests for dependencies with a 7-day cooldown; security fixes are not grouped and open at once. PyPI dependencies are ranges in pyproject.toml, locked by uv.lock. Review every Renovate pull request before merging; after merging one, wait for the others to rebase.
